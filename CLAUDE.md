## Testing

- **pytest + Playwright run on the host**, not inside the Docker image. Install once: `pip install -r requirements-dev.txt && playwright install chromium`. All E2E tests then hit `http://localhost:8000` of the running container.
- **Node.js (`node` on PATH) is also a test prerequisite** (since 2026-09-13). `tests/test_core1_return_ejectall_js.py` runs the real frontend modules under node's `vm` module, with no browser and no container, so it runs under `--offline`. It is the only hermetic proof of the CORE1 Quick-Swap Return and CMD:EJECTALL guard fixes. Without node the module skips and raises a `PytestWarning` in the warnings summary. Set `FCC_REQUIRE_NODE=1` to make a missing node a collection error.
- **⚠️ A plain `pytest tests/` run is NOT offline — it writes to real dev inventory.** This was mis-documented until 2026-08-03 and is worth internalising, because it silently shaped the whole verify cadence. The two opt-in flags guard **different services**:
  - `RUN_INTEGRATION=1` / `--run-integration` gates `@pytest.mark.integration` — tests that hit the real dev **Spoolman** on the NAS.
  - The `require_server` fixture gates tests that hit the local **FCC container** — and it skips *only when that container is DOWN*. So whenever the container is up, ~55 E2E files run on a plain `pytest`, drive a real browser, and mutate Derek's live dev data.
  - Consequence to remember: an "innocent" verification sweep is a data-mutating event on a shared container, and takes ~21 minutes (27–38 before Group 45.8 stopped the dashboard's per-tick spool-list fan-out). It is also the leading suspect for the load-sensitive E2E flake family (a captured traceback showed `test_clone_e2e` failing because a concurrent test had moved the spool it needed — not a UI race).
- **For a fast, provably hermetic check use `--offline` (or `FCC_OFFLINE=1`)**: `"C:/Python314/python.exe" -m pytest tests/ -p no:cacheprovider -q --offline`. It skips, at collection time, every test requesting a container-touching fixture (`page`, `require_server`, `clean_buffer`, `seed_*`, `scan`, …) — so no browser ever launches and nothing can write to dev. **~1.5 minutes (2,111 tests on 2026-10-14) instead of ~21 minutes.** Use it for iterating; use the full run (which includes the E2E) before committing anything that touches the frontend. Gating `require_server` alone would NOT be enough — a Playwright test can request `page` without it — hence the fixture-name list in `conftest.CONTAINER_FIXTURES`, pinned by `tests/test_offline_mode.py`.
- **`pytest --reset-dev`** restores dev to the committed seed baseline (non-destructive) before a sweep, "so cross-test contamination can't accumulate". It exists for exactly the shared-data problem above but is not yet part of the routine cadence. ⚠️ It will discard hand-made dev state, so check with Derek before using it.
- **Windows pip ↔ pytest interpreter mismatch (Derek's machine)**: bare `pip install <pkg>` resolves to `D:\Programming\Languages\Python\Python311\python.exe`, but `pytest` runs under `C:\Python314\python.exe`. Packages installed via bare `pip` are invisible to the sweep. Canonical install command for this machine: `"C:/Python314/python.exe" -m pip install <pkg>` (or `... -r requirements-dev.txt`). This bit the Group 14.5 BS4 install — beautifulsoup4 went into 3.11, the sweep imported under 3.14, and `test_amazon_parser_matching` skipped with `ModuleNotFoundError`.
- **Every run labels itself (Group 45.1, 2026-10-13).** The last line of a run is `⏱️ M:SS for N tests`; with browser tests it adds a **load factor**: the median of each passed browser test's time against the fastest time that test has taken on this PC in its last 8 runs (history in the git-ignored repo-root `/.test-timings/`). At **1.25× or more it says BUSY RUN**: treat any red as possible load noise and re-check it on its own before believing it. A failed browser test's report gains an **"FCC request log"** section (its requests over 2 s, the ones still in flight, and the dev-Spoolman read timeouts FCC wrote to `hub.log` during the test), which usually says whether a red was waiting on a slow server. ## Dryer Box ↔ Toolhead Bindings (Phase 2/3)

- **Storage**: per-slot, on each Dryer Box record in `inventory-hub/locations.json` under `extra.slot_targets` — a dict keyed by slot number (string), values are Toolhead / MMU Slot / No MMU Direct Load LocationIDs, or absent = unassigned (staging/drying).
- Example:
  ```json
  { "LocationID": "PM-DB-XL-L", "Type": "Dryer Box", "Max Spools": "4",
    "extra": { "slot_targets": { "1": "XL-1", "2": "XL-2", "3": "XL-3" } } }
  ```
  Slot 4 is absent → staging only. Split boxes (one box per printer side) are first-class; the model has no `default_printer` concept.
- **Read bindings through the one guarded reader**, `locations_db.bindings_from_row(row)`: a non-dict row or `extra` degrades to `{}`, and every falsy or blank target means unbound (a stringified `false` once made auto-deploy target a location named "FALSE"). A writer that must write `extra` back guards it with `isinstance(extra, dict)` and replaces a non-dict one. A source canary in `tests/test_slot_targets_reader_migration.py` fails on the unguarded `(row.get('extra') or {}).get('slot_targets')` pattern in `logic.py`, `routes_bindings.py`, `locations_db.py` and `placement.py` (2026-10-13; `placement.py` since Group 40.1).
- **Editing UI**: Location Manager → open a Dryer Box → "🔗 Slot → Toolhead Feeds" collapsible section. Dropdowns are grouped by printer via `<optgroup>`.
- **Single-slot boxes (a PolyDryer; Group 20.2, made spool-keyed by Group 42).** A Dryer Box with `Max Spools` `1` ("0" also counts; a blank isn't managed) is lifecycle-driven: its slot `1` binding records the head ITS OWN spool is loaded on, not a feed. It attaches when that spool deploys from it, follows the spool head to head (Derek's Q-A; only from the head it is attached to, never taking it off another head: `attach_single_slot_box_to_toolhead(..., steal=False)`), and lets go only when that spool leaves the head by any path, keyed on the leaving spool's trail through `locations_db.detach_single_slot_box`: eject, Return, any move and force-unassign (`logic._release_single_slot_box`), a wizard or `/api/spool/update` location edit (`logic.release_box_after_direct_write`), and the archive edge of a print to 0 g (`spoolman_api._release_box_on_archive`, also after a PATCH that landed but timed out). Undo re-attaches only the box the undone move released (the record's `released` / `ejection_released`). Ejecting a different spool from the head no longer unbinds it. It never auto-deploys, is never a stranger's 13.6 home, and Return's fallback never sends a stranger into it. Its spool is in slot `1` (`locations_db.effective_slot`: a blank slot reads as "1" for the box's sole occupant only); a second spool put in while another claims slot 1 (its own spool, deployed) goes in unslotted, and `/api/quickswap` refuses a slot two spools claim (`quickswap_ambiguous_slot`). A spool entering it from a non-head place records `fcc_pre_box_location` ("Pre-Box Location (system)"), so ejecting it out of the box puts it back there. The toolhead's Quick-Swap grid labels it "🔗 attached — follows #50", or a stale attachment with Unbind (read strictly, so a Spoolman blip says "couldn't read" instead; the Unbind PUT names the head it showed as `expected_target` and is refused with `binding_moved` if the box has moved since). **For a new single-spool dryer, use Type `Dryer Box` with `Max Spools` `1`**; nothing keys on the `PM` prefix.
- **Quick-Swap**: Location Manager → open a toolhead (Tool Head / MMU Slot / No MMU Direct Load) → "⚡ Quick-Swap Slots" grid aggregates every (box, slot) feeding that toolhead. Tap or keyboard-nav + Enter to swap. `Q` focuses the grid; arrow keys move; Enter triggers confirm overlay (inline div, never nested Swal).
- **Keyboard shortcut reference**: `?` button in the dashboard title bar (or the `?` key anywhere outside inputs). Any new shortcut added elsewhere should call `window.registerShortcut({id, scope, keys, description})` in `static/js/modules/shortcuts_registry.js` so the overlay stays complete.
- **Indxx forward-compat**: the model scales to an arbitrary number of toolheads by simply adding entries to `config.json:printer_map`. No schema change required for the planned Core One+ → indxx upgrade (8–10 toolheads).
- **Legacy**: the old `config.json:feeder_map` key was retired in M7. A back-compat migration in `startup_migrations.py` (called from `app.py` at import) imports a surviving install's entries into `slot_targets` on boot, but is **skipped while any Dryer Box carries a `slot_targets` key** (even `{}`; `locations_db.dryer_bindings_are_authoritative`, Group 46.4). Before that, a box whose slots were all cleared in Feeds (saved as `{}`) was silently re-bound from the stale seed on the next restart. It is a live predicate, not a latch: re-typing the only keyed box away from Dryer Box, or deleting it, re-arms the import. Harmless while dev's and prod's `feeder_map` are empty; deleting the import is the durable fix (Derek's call). Same shape as the `printer_map` seed retirement (hotfix 2026-09-29).

## Project Conventions

- **Inline overlays MUST route through `window.mountOverlay()`** (Group 15 — see [docs/agent_docs/tasks/15-canonical-overlay-mount.md](docs/agent_docs/tasks/15-canonical-overlay-mount.md) for the rationale). Don't `createElement` + `document.body.appendChild` + custom `focusin`/`keydown` listeners; the helper owns the z-index ladder, the focus-guard that defeats Bootstrap's `_enforceFocus`, host-close cleanup, occlusion of underlying selects, and idempotent teardown. Reference implementations: [weight_entry.js](inventory-hub/static/js/modules/weight_entry.js), [weight_utils.js](inventory-hub/static/js/modules/weight_utils.js) (missing-tare prompt), [duplicate_picker.js](inventory-hub/static/js/modules/duplicate_picker.js), [inv_quickswap.js](inventory-hub/static/js/modules/inv_quickswap.js) (Quick-Swap confirm), [inv_details.js](inventory-hub/static/js/modules/inv_details.js) (force-location escape-confirm).
  - **Z-index ladder** (constants on `window.OVERLAY_Z`):
    - `STANDARD = 20000` — single overlay above any Bootstrap modal/offcanvas. Pass `tier: 'standard'` (default).
    - `CONFIRM = 20100` — confirm overlay above a standard overlay (e.g. missing-tare prompted from inside WeightEntry). Pass `tier: 'confirm'`.
    - Toast layer is 11000 — intentionally BELOW overlays so a confirm isn't drowned out by toast noise.
  - **Focus guard** is the working pattern from `89c6f39`: capture-phase `focusin` listener on `document` that `stopImmediatePropagation`s events targeting the overlay subtree. Mounting INSIDE the modal subtree to escape `_enforceFocus` was tried and reverted (13.1) — it loses the z-index war. Do NOT subtree-mount overlays.
  - **Escape contract**: `mountOverlay`'s `onEscape` (or default cleanup) uses `stopImmediatePropagation`, so sibling capture-phase listeners on `document` won't fire. Callers must NOT also handle Escape — pass `onEscape: () => yourCancel()` if you need a custom cancel side-effect.
  - **Host cascade**: pass `host: someBootstrapModalEl` to auto-clean the overlay when the host emits `hidden.bs.modal` / `hidden.bs.offcanvas`. No overlay outlives its parent.
  - **No nested `Swal.fire()`** — the original prohibition stands. Nested Swals don't stack and dismiss each other; route confirmation dialogs through `mountOverlay` instead.
  - **Z-order incident symptom checklist** — each symptom maps to a `mountOverlay` behavior; if you see one, suspect a bypassed `mountOverlay`:
    - Click triggered something but I can't see it → mount target wrong (must be `document.body`).
    - Overlay rendered behind sibling modal chrome → wrong tier or subtree-mounted.
    - Brief processing flash then "nothing" → overlay closed itself but parent listener didn't know.
    - Inline overlay's Escape closes BOTH the overlay and its host modal → caller is also handling Escape; let `mountOverlay` own it.
    - Overlay lingers after host modal closes → didn't pass `host`.
    - `<select>` dropdown under the host intercepts overlay clicks → didn't pass `occlude`.
- **Bootstrap gating dialogs (`#confirmModal` / `#safetyModal` / `#actionModal`) — never `.show()` / `.hide()` them directly (2026-09-12).** Go through `requestConfirmation` / `promptSafety` / `promptAction` / `closeModal` (`inv_core.js`). Bootstrap 5.3 silently IGNORES `show()` while a modal is fading out and `hide()` while it is fading in; FCC re-prompts from inside a dialog's own callback (eject → active-print re-confirm → "true unassign"), so a direct call drops the prompt with no error and leaves its callback armed. The helpers track each dialog's phase from Bootstrap's public events and queue the one call Bootstrap would drop. A CONFIRM scan may fire a callback only when `window.isGatingModalOnScreen(id)` (fully shown AND hit-tested visible — a `mountOverlay` panel can cover a Bootstrap modal); a fading dialog is click-inert via `global.css`. Pinned by `tests/test_confirm_chain_reshow_e2e.py`. Symptom of a bypass: "clicked YES, the second prompt never came, and nothing happened".
- **Move confirms name their heads (Group 39).** `perform_smart_move`'s `confirm_active_print` is `True` (every head: `execute_bulk_move`, whose plan already skipped every loaded spool), falsy (none) or a **list of head ids**: the active-print warnings the user actually saw. The browser's move doors (`manage_contents add`, `/api/smart_move`, the `identify_scan` slot branch, `/api/quickswap`, `/api/quickswap/return`) read `confirmed_toolheads` through `logic.confirmed_heads`, and a bare legacy `confirm_active_print: true` covers **no** head. A page loaded before Group 39 only ever sends that bare flag, so when such a request would be asked again the door answers its own error shape with `logic.STALE_PAGE_MSG` ("reload the page") via `logic.stale_confirm_refusal`, instead of a question it can never answer. Eject, force-unassign, clear-location and the bulk-move commit keep their boolean. A Yes always sends the UNION of every head confirmed so far (`window.unionConfirmHeads`), or two printing heads ping-pong the user. The engine answers ONE confirm per move in the shape `_requires_confirm_answer` builds (`active_prints` with roles `destination` / `feeds` / `source`), after the strict reads of the pre-write contract (the comment block in `_perform_smart_move_impl`; extend a step, never reorder it). Its message names every head the Yes covers: a bound slot's `feeds` head always gets its own sentence. A re-scan onto the spool's own head asks nothing unless Smart Load would unload another spool. When step 5 could have probed, step 6 re-lists the head strictly before Smart Load (a load that landed during the probe is unloaded too, except by the auto-deploy chain: its guard, `fed_check_from` (40.0c), refuses to unload a spool the question didn't show, and the incoming spool stays stored in its slot). A new door shows `window.confirmActivePrint` (inv_core.js), never a new copy of the overlay, and a door's re-ask shows the server's `msg` (Quick-Swap, Return and the deposit share `_reaskFromServer`).
- **A bound box slot asks before loading over a spool from elsewhere (Group 40.0c), and a slotless move gets its slot first (40.0e).** A move into a multi-slot Dryer Box slot whose binding is a toolhead answers `requires_confirm` / `confirm_type: "head_fed"` when that head runs a spool whose trail is not that very box and slot (no trail asks too); the slot's own spool coming back out asks nothing. The answer is the 39.1 shape plus `fed_heads` (each with a `confirm_key`, "XL-1#99": the head and the spools it ran), `can_store`, `target_slot`, `spools`, `title` and `body` (a printing-only answer on a bound slot carries `can_store` / `title` / `body` too). "Load it instead" replays with the keys in `confirmed_fed_heads` (a key covers the head only while it runs exactly those spools; a bare head id covers it whatever it runs, for internal callers); "Just store it" replays with `auto_deploy: false`. The three doors (`manage_contents add`, `/api/smart_move`, the `identify_scan` slot branch) read them through `logic.confirmed_fed_heads_from` / `logic.auto_deploy_requested`, and a request **without** the `confirmed_fed_heads` key gets `logic.stale_fed_refusal`'s "reload" instead of the question, so **every browser call of those doors sends `confirmed_fed_heads` (even `[]`)**. A slotless single spool into a multi-slot box gets its slot at step 3 from `logic.recommend_box_slot` (the slot picker's ⭐ rule) before anything is asked; answers carry it as `target_slot`, and a replay sends it back as `picked_slot`, which is kept only while still free and never unseats anyone. The chained deploy refuses to unload a spool that reached the head after the question (`fed_check_from`), whatever its trail. Builder notes for the browser half: `docs/agent_docs/tasks/40-slot-picker.md`, 40.3.
- **One move question, one replay builder, and a replay names the feed it was asked about (Group 40.3; Derek, 2026-10-14).** The browser shows every move question through `window.askMoveConfirm` (inv_core.js): a `head_fed` / `feed_changed` answer, or an `active_print` one with `can_store`, opens the three-way "Load it instead / Just store it / Cancel" (a mode of `window.confirmActivePrint`; Enter stores, its QRs are `CMD:CONFIRM:<sid>` / `CMD:STORE:<sid>` / `CMD:CANCEL:<sid>`, other scans are held off while it is open, and it is drawn as a printing question when the answer says `printing`); every replay is built by `window.buildMoveReplay`, and every "stored" toast ends with `window.storeToastTail` ("— XL-1 left as it was", or "— taken off XL-1" when the spool left that head). A new door uses all three, never a copy. One unanswered question per overlay id: a dialog mounted over an unanswered one on the same id settles it as superseded (`onCancel({superseded: true})`; `confirmActivePrint` logs it for every caller, never toasted as "Cancelled"), and scans stay held off while ANY three-way is open (`window._fccOpenMoveQuestions`; answering the newer of two must not free a scan behind the older). Every `requires_confirm` a move answers carries `target`, `target_slot`, `slot_picked` (the engine chose that slot: a replay sends it back as `picked_slot`, otherwise it re-sends its own `slot`), `feed` (for a multi-slot Dryer Box target: what the target slot feeds, a head id or `""` for an unbound / Printer Pool slot or no slot; `null` for any other target) `can_load` (the Yes loads the slot's head) and `leaving` (the heads the moving spools leave, printing or not: the store toast says "taken off XL-2" for those). Every replay sends `expected_feed: answer.feed`, and so does a screen that showed the slot's feed when the user chose it (the Quick-Swap deposit tile); a blind slot-label scan never does, so a first scan into a bound slot stays prompt-free. When the slot now feeds something else (re-pointed; a pool or unbound slot now bound to a head; a full box that freed a slot), the engine writes nothing and answers `confirm_type: "feed_changed"` with `feed_changed: {was, now}`, the new head's `fed_heads` (residents an old confirm key covers are named again) and `active_prints`, and `title` / `body` / `msg` ("LR-MDB-1 slot 1 now feeds XL-2 (it fed XL-1 when you were asked). Load #57 onto XL-2?"), even for an empty idle head. A store replay is asked again as a store, offering no load and reading no head ("… Store #57 in LR-MDB-1 slot 1?", `can_load: false`; the browser keeps a chosen store a store, Group 40.3 review), and so is a load whose new feed loads nothing (a pool, no toolhead, a non-head binding). Single-slot boxes (their slot-1 binding is the lifecycle attachment) and head targets ignore `expected_feed`. The three doors read it through `logic.expected_feed_from` (absent or null: no check; a non-string reads as `""`, toward asking), and the `identify_scan` slot branch relays every key of the engine's answer. At the doors `stale_fed_refusal` runs BEFORE `stale_confirm_refusal`: a pre-Group-39 page asked a `head_fed` question must hear "XL-1 is running #99 … reload", not "can't confirm a move during a print"; a `feed_changed` answer reaches neither rule (only a page that sends `expected_feed` gets one). A slot bound to something that isn't a toolhead never chains: the spool stays in its slot and `auto_deploy_skipped` says why. The three-way's store (Enter) is offered on a printing answer only when the head the slot loads is itself mid-print; a print on the head the spool only leaves keeps the yes / no. **`seen_printing`** (head ids, `logic.seen_printing_from`): the toolheads a page saw printing (the Quick-Swap deposit sends it when its own probe sees a print and leaves the question to FCC); for that whole move their printers count as printing whenever the move's probe fails open, so the question never hangs on a second probe. A slot whose own spool runs on a head OTHER than the one the slot feeds (re-pointed after it was loaded) takes no new spool on any path ("… still holds #60, loaded on XL-3, while the slot feeds XL-1: take #60 off XL-3 first"). A stale trail (its spool is on no head: a wizard / `/api/spool/update` Location edit keeps the trail) never blocks a load, as it never did; a store over one is refused and says what it is ("… is still claimed by #60, whose record says it came from there, though it is on CR-CT-2-R2: scan #60, then CR-CT-2-R2's label, to clear that").
- **The slot picker writes nothing and tells its caller what to send (Group 40.2).** `window.openSlotPicker` (`slot_picker.js`, model `placement.py`) resolves a box-slot pick with `send` (`{picked_slot}` for a free slot or the spool's own; `{slot}`, the engine's Overwrite, only after the user chose Swap / Overwrite / Swap it out / Put it in slot N in the picker's own panel, with `auto_deploy: false` added where the tile said "stored here, not loaded back", the engine's store_only rule) and `expected_feed` (the tile's feed: a head id or `''`), which a door sends on its FIRST request so a slot re-pointed meanwhile is asked again, plus `swap` / `displaced` (a Swap: the door buffers the old spool once the move lands) and `store_ok` (false over a stale record: the door's question then offers no "Just store it", `askMoveConfirm`'s `ctx.noStore`). It refuses to open over another `mountOverlay`, an audit, a gating dialog or a busy page, closes itself when a bulk move or an audit starts, and greys out the slots the engine would refuse (`blocked`, with the reason on the tile and in the panel's `role=alert` status line). A digit is a hotkey only when nothing follows it within 50 ms (a digit within 300 ms after one makes both a scan, and the highlight goes back), a scan in flight or two characters in the scan buffer own the Enter, and a lone digit is dropped from the scan buffer in every view. Only the picker's own bare `CMD:CANCEL` cancels it (a stale `CMD:CANCEL:<sid>` is ignored). `performContextAssign` reports how its move ended to `opts.onOutcome({outcome: moved | cancelled | failed})` for a door that loops (the box label: one picker per buffered spool); it returns nothing, because a returned Promise made a test's `page.evaluate` wait on a question it could only answer afterwards (a 30-minute hang). New picker doors (40.4–40.7) use this contract, never their own Swap / Overwrite.
- **A location label read twice is read once (Group 40.2 review).** A scanner's double-read of a slot label, queued while the first read was handled and replayed after it, reversed a same-slot swap and, in the box picker's loop, picked a slot for the next spool. `processScan` drops an identical `LOC:` scan read before the last one was answered or within 1.5 s after (`capturedAt` from the accumulator in `scripts.html`; toast + INFO log), and the identify_scan slot door holds back, for `logic.SWAP_BACK_GUARD_S` (2 min), a blind scan whose buffer top is the spool the same-slot swap just took out of that very slot (`logic.swapped_back_refusal`, answered `assignment_held`, nothing written; Undo Last Move is the way back). A door that names its spool is never held back.
- **Keyboard nav idiom**: arrow keys move a `.kb-active` class between focusable items (wraps at edges), Enter confirms, Escape cancels or prompts. Auto-focus the primary input when a modal opens. Force Location modal + Quick-Swap grid are reference implementations.
- **Activity Log + Toasts**: every scan outcome (success, warning, error, partial) writes an Activity Log entry AND raises a toast. ## Spool / Filament write surfaces

Every code path that calls `spoolman_api.update_spool` or `update_filament` has the same two failure modes: (1) Spoolman replaces the whole `extra` dict on PATCH so partial payloads silently wipe siblings; (2) on rejection both functions return `None` and most callers don't surface the actual error body. Both are the root of the 2026-04-26 / 2026-04-27 prod outages.

Conventions every write surface MUST follow:

- **Use the helper, not inline diff loops.** `spoolman_api.compute_dirty_extras(existing, requested, system_managed=...)` returns `(dirty_dict, stripped_keys)`. Pass `system_managed=spoolman_api.SYSTEM_MANAGED_EXTRAS` whenever the surface is user-driven editing (wizard, vendor edit modal, manufacturer edit modal, etc.) — that frozenset enumerates the keys owned exclusively by `perform_smart_move` / `perform_smart_eject` (`container_slot`, `physical_source`, `physical_source_slot`) and FCC's own breadcrumbs (`fcc_pre_archive_location`, `fcc_pre_audit_location`, `fcc_pre_box_location`). Every Undo and Smart Load snapshot writes them all, and Spoolman rejects a whole PATCH carrying an unregistered extra, so a new one goes into `REQUIRED_SPOOL_EXTRAS` (startup registers it) and `setup_fields.py` in the same commit.
- **Surface `LAST_SPOOLMAN_ERROR` on failure.** Both `update_spool` and `update_filament` populate the module-global on every rejection (the symmetry was fixed 2026-04-27 — pre-fix, only `update_filament` did). Read it in your `else:` branch and either (a) write to the activity log via `state.add_log_entry(..., "ERROR", "ff4444")`, or (b) return it in the JSON response so the frontend can `showToast(err, "error", 7000)`.
- **For high-stakes paths use `_or_raise`.** `update_spool_or_raise` and `update_filament_or_raise` raise `spoolman_api.SpoolmanRejection` instead of returning `None`. Use these on slot assignment, label-confirm scans, force-move, and weigh-out — paths where silent failure left the user with no signal.
- **Don't add `force_reset=True` to `setup_fields.py` lightly.** A field-schema delete wipes that extra on every record. The existing `migrate_container_slot_to_text()` is the template for any future legitimate type migration: snapshot values, force_reset, restore. Steady-state setup_fields runs MUST be value-preserving.
- **To DELETE an extra, send the delete-sentinel — don't omit the key (Group 23.4).** Because the read-merge starts from the full existing extras and only overlays keys the caller SENT, an OMITTED key means "keep" (the sibling-wipe guard). A blanked field can therefore never be cleared by omission. A surface that wants to clear an extra sends `spoolman_api.DELETE_EXTRA_SENTINEL` (frontend: `window.FCC_DELETE_EXTRA`, defined in `inv_core.js`) as that key's value; `_merge_extras_with_existing` pops it (it is NEVER forwarded to Spoolman or stored literally), and `_is_delete_sentinel` matches the quote-stripped form so it survives `sanitize_outbound_data` wrapping. The merge refuses to pop a `SYSTEM_MANAGED_EXTRAS` key even if sent the sentinel (slot-binding backstop), and `compute_dirty_extras` suppresses a sentinel for an absent/blank key (no spurious PATCH). Edit surfaces should only emit the sentinel in EDIT mode (on CREATE a blank is just omitted). Edit-log formatters render it as `→ (cleared)`. Pin behavior with `tests/test_delete_sentinel.py` (the spoolman_api merge helpers) + `tests/test_l316_charact_filament_edit_log.py` (the formatter's `(cleared)` render).

## Multi-agent Workflow budget

**Before launching a multi-agent `Workflow`:** state the agent count + rough cost
first. **Batch the verify stage** — never one agent per finding (that is what blew
a usage window on 2026-08-02: 55 findings → 55 verifiers; re-running the same
review at 14 findings/agent cost 710K tokens instead of 4.4M, with zero agent
errors and *more* usable signal). If the fan-out is large and the current usage
window is unknown, ask for quota / reset time / work-headroom before starting.

This subscription is shared with Derek's **paid work** (a separate machine and
workspace — everything in this repo is a hobby project), so an oversized burst
here can block real work. Quality is NOT the thing to cut: keep the effort and
the rigor, shape the fan-out better and defer optional depth to an idle window.
Night/scheduled work must never sit on the critical path, and scheduled agents
start with zero context so they need self-contained instructions. Pay-as-you-go
credits exist but are a **last resort** — propose and discuss, never assume.
