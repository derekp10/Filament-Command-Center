## Decisions

### Derek's two calls (each written to be asked cold, one at a time)

**63.1: What should an archived spool remember as its last place?**
- **What it is.** When a spool is weighed or printed down to 0 g, FCC archives it, files it as Unassigned, clears its slot, and writes the place it left into a hidden note, "Pre-Archive Location (system)" (you can see it in Edit Spool's Spool Extras). The note has one job: if that spool is later weighed back above 0 g (a typo fixed, a spool that wasn't really empty) or Archived is unticked, FCC sends it back to the noted place. The weigh-out list takes spools off toolheads, so the note is often a toolhead.
- **Where.** `spoolman_api._auto_archive_on_empty` writes the note; `_auto_unarchive_on_refill` and `_unarchive_destination` use it.
- **A real example** (dev's copy of your inventory, made 2026-11-13; prod not read). 13 archived spools carry a note. #226's says XL-3, #241's XL-2, #95's RCOI-5 and #99's RCOI-1. Weigh #226 back to 300 g and FCC puts it on XL-3 if XL-3 is empty, or files it Unassigned with a warning if another spool is there. Three more say CORE1 and one CORE1-M0, places that no longer exist (those go Unassigned with a warning). #213's says LR (a room), #24's LR-MDB-1, #267's PM-DB-9.
- **Your words (2026-11-14):** *"Toolhead doesn't make sense, but room might instead. Blanking is also an option, with the exception of reusable spools (which will get a new label anyway.) most expired spools get tossed."*
- **The options:**
  - **(a) The head's room.** Save the room its printer stands in: XL-3 becomes LR, RCOI-5 becomes CR (the rule Smart Load already uses for a spool with no home). One more choice comes with it: is a room note a place to go back to (a refill leaves the spool loose in that room, which eject stopped doing in Group 41.8 because loose room spools are hard to find), or only a record of where it was (a refill files it Unassigned, and the note just tells you where it had been)?
  - **(b) Blank.** No note when the spool was on a toolhead: a refill files it Unassigned, as one does today when the toolhead holds another spool. Boxes, carts and shelves keep their note.
  - **(c) Keep it as now.**
- **Two small parts of the same call:**
  - **The 4 notes that already name a toolhead** (on dev; prod not read). Under (a) or (b): read them by the new rule from now on, or leave them working as today. Nothing is rewritten either way. Recommendation: read them by the new rule.
  - **Reusable spools.** Nothing in FCC marks one. The nearest is the "Is Refill" box (true on 18 of dev's 301 spools; set by the first spreadsheet import or by hand, and read by no FCC code). "Spool Type" (Cardboard, NFC Plastic, Plastic) says nothing about reuse. What should a reusable spool's archived record keep, and how should FCC tell one apart? Recommendation: nothing special. Its next coil is a new spool record with a new label, as you said, so the old record's note is never used. Is Refill stays unread until a feature needs it.
- **Recommendation:** (b), with the old toolhead notes read the new way and no special case for reusable spools. A toolhead is the one place a refilled spool shouldn't jump back onto by itself (it is in your hand, not on the printer); a box or a shelf is a real home.
- **If you don't answer:** (c). The note keeps saying what it says today. The four fixes under "Claude's calls" still go in.

**63.2 (🟠): A spool weighed to empty that FCC couldn't take off its place. Retry, list, or both?**
- **What it is.** Rare: it needs Spoolman to fail twice in a row (restarting for an update, a network blip, "database is locked"). FCC can't read the spool before the save, so it skips its own step that files an emptied spool as Unassigned, the save archives the spool where it stands, and the weigh page's follow-up "take it off" request fails too. The spool is archived but still on its toolhead or in its slot, with no pre-archive note. FCC says so once (a 7 s warning, a line on the empty-weight prompt, a WARNING line in the Activity Log), then forgets it.
- **Where.** The weigh screens' save (`saveSpoolWeight` and its "take it off" request, `inv_weigh_out.js`) and the refill edge (`_auto_unarchive_on_refill`).
- **An example.** You weigh #57, loaded on XL-1 from LR-MDB-1 slot 2, down to 0 g while Spoolman restarts for an update. The warning says "Spool #57 is archived but still at XL-1: FCC couldn't take it off there." Every FCC list hides archived spools, so XL-1 looks empty and you load #99 there. Weeks later you find a little left on #57 and weigh it: FCC puts #57 back in stock on XL-1, beside #99, still claiming LR-MDB-1 slot 2.
- **Your words (2026-11-09):** *"we'd want to follow up with making sure this was set to the default location for archives ... so we need to make sure it's reported somewhere for the user to either manfually fix or code fixes it. (Not srue why spoolman would refuse, so that's a case that might need to have some protections and cautions around.)"*
- **The options:**
  - **(a) FCC keeps trying.** It writes the spool down in a small file on disk (like the print deduct's download queue) and keeps trying to take it off the way a normal archive does (Unassigned, with the pre-archive note, slot and trail cleared) until that lands.
  - **(b) FCC lists it for you.** An Activity Log line naming the spool and its place, with a "Take it off" button, shown again after every restart while it waits (the 🛑 review line's pattern).
  - **(c) Both.** It retries, and lists only what still hasn't landed after a few tries.
- **Either way (Claude's call):** a refill never puts a spool back where another spool is now, whether that is a toolhead, a one-spool box or a box slot. It files it Unassigned with the same warning a taken toolhead gives today. This also closes a hole found while checking: today a refill sends a spool back into a one-spool dryer box (like PM-DB-9, which #267's note names) without checking that the box is empty.
- **Recommendation:** (c). Most cases fix themselves within a minute; only a Spoolman that stays broken leaves anything to list.
- **If you don't answer:** (c), with the listed line shown to you as a picture before the merge.

### Claude's calls (for veto)
- **63.1, whatever Derek picks (the same trace's findings):**

## Design

**Build order:** Derek's two answers (if not asked yet) → 63.3 → 63.1 (the archive helper) → 63.4 with 63.2 → 63.5 → 63.6 → 63.7 and 63.9 → 63.8 last (after 62.4's `trapTab` and 63.9(b)'s box change are in) → a review from `docs/agent_docs/review-checklist.md`, its fixes, the full run, the pictures, Derek's OK.

### 63.1
- One helper writes an archive's outcome (e.g. `spoolman_api._archive_outcome(existing)`): location blank; slot and trail blank; `fcc_pre_box_location` blank when set (63.4); and `fcc_pre_archive_location` set to the place by Derek's rule, or written empty when there is none (a spool at Unassigned, at Unknown, or on a toolhead under (b)). The weigh edge, `_take_archived_off` (which keeps writing no place: the person asked for the spool somewhere else) and 63.2's take-off all use it.
- (a): `_known_room_of` moves into `locations_db` (logic calls it there), and the room note is a place or a record by Derek's sub-answer. (b): one condition (a printer-map head, a toolhead-type row, or a Printer row that is its own head gets no place). Old toolhead notes are read by the same rule at the refill; no data is rewritten.
- The refill restores the noted place only while the spool is Unassigned; otherwise the spool stays and the note is used up. A note "UNKNOWN" reads as none.
- In `update_spool`, any write that takes a spool out of the archive writes `fcc_pre_archive_location: ''`, unless the caller sent it. `perform_undo` doesn't write back `fcc_pre_archive_location` for a spool it leaves in stock.

### 63.2
- **The take-off, in the route.** When `/api/spool/update`'s write archived a spool (not archived before) that is still at a place, the route takes it off in the same request with 63.1's helper, working from the record Spoolman just answered (no extra read), and releases its single-slot box. It asks nothing about a print, as the archive edge never has (a spool weighed empty is in the person's hand; the page's request sends `confirm_active_print: true` today for the same reason). `location_now` says where it ended; a new `still_at` names the place when the take-off failed, so the page's warning words stay. The page stops posting `force_unassign` after a save.
- **(a) the retry.** A take-off that fails goes into a small store (e.g. `data/pending_archive_takeoffs.json`, a flat module beside `cancel_fetch_store.py`, reading `FCC_DATA_DIR` once at import as the four stores do). The print monitor's loop retries due entries: first after ~30 s, then backing off. Each try re-reads the spool strictly (`get_spool_answer` plus its id): a spool refilled, moved or deleted since is dropped with an INFO line; otherwise the helper's write, and when it lands one INFO line and the entry goes.
- **(b) the list.** After 5 failed tries (or at once, under (b) alone), one WARNING Activity Log line names the spool and its place, with a "Take it off" button (a delegated click, the 🛑 review line's pattern) that runs the same take-off through a small new route. The line comes back at every restart while the entry waits (`startup_migrations`, as for cancel reviews).
- **The protection, either way.** `_auto_unarchive_on_refill` treats a spool still archived at a place as if its note named that place, its slot included. `_unarchive_destination` checks every one-spool place (a printer-map head, a toolhead or Printer row, a single-slot dryer box, a row whose Max Spools is 1) and a multi-slot box's slot (another spool claiming it, by the one slot rule). Taken, or unreadable: Unassigned, slot and trail cleared, the 42.3c warning. The one-spool tests it needs move into `locations_db`.
